OBJ: Expand agent capabilities connecting it to real-world data and actions via standardized protocols.
IN: External service to integrate (API, database, MCP). Expected data schema.
OUT: Configured MCP or API integration, defined schemas, published catalog tool.
DEPS: Composio MCP (primary path) and/or MCP brachat-mcp boundary (API keys via mcp_secrets_get).
TOOL ARCHITECTURE GUIDELINE (approved Fabio 02/aug/2026): MCP for external/agentic integrations: Composio (apps), n8n (workflows), mem0, brachat-mcp — everything the agent must see as a tool and call. One protocol, standard auth, skill-gate by prefix. Native CLI/LIB for deterministic internal operations: git, docker, node/python one-offs, file read/write. No MCP — each MCP server adds schema to context (token cost) without benefit here. Practical rule: MCP to expose/make accessible; CLI/LIB to execute system operations. Composio continues serving external apps; n8n becomes its own MCP server; libs stay direct. EXCEPTION: putting an internal tool on MCP only with explicit Fabio authorization. Reference: `.opencode/reference/manifest_tools.txt` (minimum verification rule + static summary).
COMPOSIO ACCESS: on-demand activation — Composio stays OFF at boot (schema cost). Activate only when the task requires real integration, via `/mcp` toggle. Scope: exclusively for connecting external tools (Gmail, Google Calendar, Slack, Notion, CRMs, etc.) through Composio MCP tools. Auth: credentials via OAuth/secret manager (env vars). Never hardcoded in repo. Flow: 1. Verify needed tool available in Composio MCP. 2. Activate server via `/mcp` when dependency confirmed. 3. Execute integration with aggressively validated schema. 4. Deactivate via `/mcp` when done (return to lean boot). Security: every integration passes the External Integrations Rule of governance-policy. Writing to external APIs = High risk → explicit Fabio approval. Cost: each MCP tool adds schema to context. Integrate only strictly necessary tools.
PROTECTED BOUNDARY ACCESS (brachat-mcp): sensitive data (credentials, PII, personal docs) lives in `.opencode/mcp/` and is accessible ONLY via MCP server `brachat-mcp` (`.opencode/mcp/server.mjs`). opencode permissions block direct read/write of `.opencode/mcp/**` (Read/Edit/Glob deny). NEVER bypass via bash/cat. Tools: `mcp_list`, `mcp_read`, `mcp_write`, `mcp_secrets_list` (names only), `mcp_secrets_get` (1 key, audited in `.opencode/mcp/audit.log`). Rules: credentials never via `mcp_read`; write blocked in `credentials/`, `server.mjs`, `README.md`, `audit.log`. Path traversal and binaries blocked in server.
REMOTE MCP ACCESS (OCI): after OCI migration, same server runs via HTTP in `.opencode/mcp/server-remote.mjs` (deploy with `.opencode/infra/ezra-core/`). Endpoint: ALB + listener 8765 → instance `ezra-prod` (private); healthcheck in workflow `restore-test.yaml`. Auth: `Authorization: Bearer <token>` — same value as secret `ezra/brachat-token` in Vault (never in client code/env). Boundary: `/ezra-data/mcp`; secrets in `/ezra-data/.secrets.env` (0600, populated by `.opencode/iac/scripts/fetch-secrets.sh` directly from Vault, no keys on disk). External access: credentials and boundary reads ONLY via MCP tools — never by direct file/ssh read. Fallback: if ALB is down, first validate `deploy.yaml`/`backup.yaml` before any action.
