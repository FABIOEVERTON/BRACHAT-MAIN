DESC: Deterministic code engineering protocol for writing, fixing, reviewing or refactoring any code, with SPEC, type contracts, path mapping and adversarial self-review.
TITLE: Code Engineering — Deterministic Protocol. Deterministic code engineering protocol for agents operating with multiple LLMs. Use this skill ALWAYS when writing, fixing, reviewing or refactoring any code — regardless of language, framework or file size.
MANDATORY TRIGGERS: "write a plugin", "fix this code", "implement X", "refactor Y", "create a module", "add a function", "review this file". Never write code without following this skill.
This skill defines the mandatory paths any agent must traverse to produce correct, auditable, regression-free code. Derived from forensic analysis of real errors in `memory-core.ts` and `memory-persistence.ts`.
WHY AGENTS ERR CODE (observed errors → root cause → preventing phase):
`Array.isArray(state.audit)` guarding an object | condition written without checking type invariant | PHASE 3 — Contracts.
`readState` called twice in `dailyZeroIfDue` | state ownership not mapped before delegating | PHASE 4 — Paths.
`Record<string, any>` in all signatures | typing deferred and never refined | PHASE 3 — Contracts.
`readState` threw on first run | "absent state" path not mentally executed | PHASE 4 — Paths.
`.catch(() => {})` silencing failures | failure path not modeled | PHASE 4 — Paths.
`type: "user"` reading `output.parts` of assistant | hook signature not read before assuming source | PHASE 2 — Dependencies.
Fields `"pending"` and `token_cost: 0` never replaced | spec never defined what each field must contain | PHASE 1 — SPEC.
State initialized externally without documentation | initialization responsibility not specified | PHASE 1 — SPEC.
PROTOCOL STRUCTURE:
PHASE 0 — Stop and read
PHASE 1 — Specification (SPEC)          ← mandatory before any code
PHASE 2 — Map external dependencies
PHASE 3 — Define type contracts
PHASE 4 — Map all execution paths
PHASE 5 — Write the code
PHASE 6 — Adversarial self-review
PHASE 7 — Delivery
No phase can be skipped. If a blocking phase cannot be completed (e.g. missing file), declare the block explicitly before proceeding with assumptions marked `TODO:UNVERIFIED`. PHASE 1 (SPEC) is the gateway for all implementation work. No line of code is written before the spec is complete and validated.
PHASE 0 — STOP AND READ. Before writing any code:
0.1 Inventory what exists: list all files mentioned/referenced by the code to be written. For each file: available? fully read? If not available: explicitly declare what is unknown.
0.2 Identify task type: NOVO/NEW (file does not exist) | run complete PHASES 1-7. CORRECÇÃO/FIX (bug in existing code) | read full file before any edit. ADIÇÃO/ADDITION (new function/module in existing base) | read all files the addition touches. REFACTOR (structural change without behavior change) | map all callers before changing signatures.
0.3 Declare what was not read. If any dependency missing, write explicitly:
BLOCK: [filename] not available.
Assumptions made: [list].
Risk: [what could be wrong if assumptions fail].
PHASE 1 — SPECIFICATION (SPEC). No code before this phase completes. The spec is the contract between what was asked and what will be implemented. Spec errors produce correct code for the wrong problem.
1.1 What this code must do (observable behavior). Describe in natural language, without code: input? (types, format, constraints). output? (types, format, constraints). What happens in each error case? Who is the caller? (another module, framework hook, CLI, test). Mandatory format:
SPEC: [function/module name]
ENTRADA/INPUT:  [description]
SAÍDA/OUTPUT:   [description]
ERROS/ERRORS:   [what each failure type must produce]
CHAMADOR/CALLER: [who uses this and how]
1.2 Responsibilities and boundaries. For each function/module to create, declare explicitly: what is THIS function's responsibility? What is NOT this function's responsibility (delegated where)? Who owns shared state? Example from real error — undeclared responsibility:
PROBLEM: dailyZeroIfDue owned state but delegated to appendEpisodic which also read and wrote the same state. Neither had documented responsibility.
CORRECT SPEC:
  dailyZeroIfDue: STATE OWNER during its execution.
  Responsibility: read once, modify in memory, write once.
  appendEpisodic: must NOT be called internally — inline the modification.
1.3 Data fields: what each one means. For each struct/interface/config field: concrete type? empty/initial value? How computed? (who fills it, when, from which source). What does it mean if empty/zero/null? Example from real error — fields without spec:
PROBLEM: state_hash_before and state_hash_after were written as "pending" because spec never defined what those fields must contain.
CORRECT SPEC:
  state_hash_before: string — truncated SHA-256 (16 chars) of state before operation. Computed in: tool.execute.after, before calling the tool. Source: hashState({ tool, sessionID, phase: "before" })
  state_hash_after:  same, with phase: "after", computed after execution.
  token_cost:        number — operation token cost. Source: exposed by memory-core via API (not yet available). Value while unavailable: 0 with explicit TODO:UNVERIFIED.
1.4 Initialization and first run. For any state-persisting module: who creates initial state? (this module? external module? user?). What happens if state does not exist when this code runs? Must the function auto-initialize or throw? Rule: if the function may be the first to run, it must auto-initialize. If it depends on external state, it must explicitly declare that prerequisite. Example from real error — unspecified initialization:
PROBLEM: readState threw if state.json did not exist. No spec defined who created the initial file.
CORRECT SPEC:
  readState: if state.json absent → create with emptyState() and return.
             Responsibility: auto-initialization on first run.
             Prerequisite: none — must work in a clean environment.
1.5 SPEC checklist before advancing:
- [ ] Input and output of each function described?
- [ ] Responsibility of each function delimited?
- [ ] Shared state owner declared?
- [ ] Each data field has: type, initial value, source, empty semantics?
- [ ] First-run behavior defined?
- [ ] Behavior on each error type defined?
- [ ] Who calls each function identified?
PHASE 2 — MAP EXTERNAL DEPENDENCIES. For each import, SDK, hook or external API used:
2.1 Verify real signatures. Never assume parameters from memory. For each function called from external module: return type? mandatory parameters? sync or async? what does it do on failure? Example of real error:
// WRONG — assumed signature
flushMem0(root).catch(() => {})  // what does flushMem0 return? Promise<number>? void?
// CORRECT — signature verified first
// flushMem0(root: string): Promise<number>  ← read in memory-core.ts
// Returns number of sent entries. Rejects if fetch fails.
flushMem0Safe(root)  // wrapper with explicit failure log
2.2 Verify hook semantics. For any framework/SDK hook: who calls this hook? (framework, user, system). What does input contain? What does output contain? Are output data from assistant, user or system? Example of real error:
// WRONG — assumed semantics
"chat.message": async (_input, output) => {
  appendShortTerm(root, { type: "user", ... })  // WRONG: output = assistant response
}
// CORRECT — after verifying hook contract
appendShortTerm(root, { type: "assistant", ... })
2.3 Verify absent-state behavior. For any function reading persisted state (file, DB, cache): what happens if file/resource does not exist? Throws? Returns null? Returns default? Does the caller handle this case? Example of real error:
// WRONG — throws on first run
export function readState(root: string) {
  if (!existsSync(p)) throw new Error(`state.json nao existe: ${p}`)
}
// CORRECT — initializes on first run (per SPEC 1.4)
export function readState(root: string): AppState {
  if (!existsSync(p)) {
    const initial = emptyState()
    writeFileSync(p, JSON.stringify(initial, null, 1) + "\n", "utf-8")
    return initial
  }
  return JSON.parse(readFileSync(p, "utf-8")) as AppState
}
PHASE 3 — DEFINE TYPE CONTRACTS.
3.1 Never use `any` as working type. `Record<string, any>` and `any` are forbidden in public signatures. Allowed only in temporary cast with comment explaining why and with `TODO:` for removal.
// FORBIDDEN in public signature
export function readState(root: string): Record<string, any>
// REQUIRED — derived from SPEC 1.3
export interface AppState {
  memory: StateMemory
  audit: { events: unknown[] }
  session?: { last_zeroed?: string }
}
export function readState(root: string): AppState
3.2 Define interfaces before implementing. Mandatory order: 1. Write interfaces/types (derived from SPEC 1.3). 2. Write `emptyState()` or equivalent respecting the interfaces. 3. Only then write functions operating on those types.
3.3 Verify type invariants before writing guards. For each type guard (e.g. `if (!Array.isArray(x))`), execute mentally with 3 concrete values: Value 1 (expected type on happy path) | guard must let pass. Value 2 (corrupted type, e.g. array) | must initialize. Value 3 (absent undefined/null) | must initialize. Example of real error:
// WRONG — inverted logic, not tested with concrete values
if (!Array.isArray(state.audit)) state.audit = { events: [] }
// Array.isArray({events:[]}) === false → initializes → OK by accident
// Array.isArray([])          === false → FALSE → does not initialize → corrupted state
// CORRECT — explicit type check, tested with the 3 values
if (typeof state.audit !== "object" || state.audit === null || Array.isArray(state.audit)) {
  state.audit = { events: [] }
}
3.4 Types checklist before advancing:
- [ ] All public signatures have concrete types (no `any`)?
- [ ] All interfaces have a constructor/factory (`emptyState`, `createX`)?
- [ ] All type guards verified with 3 concrete values?
- [ ] Async function return types declared (`Promise<T>`)?
PHASE 4 — MAP ALL EXECUTION PATHS.
4.1 State ownership. For any function reading and writing shared state, map the full cycle before writing:
READ → MODIFY → WRITE
Rule: between READ and WRITE, no other function may read or write the same state. If a sub-operation needs state, it receives state as parameter — it does not read disk again. Example of real error:
// WRONG — reads state twice creating race condition
export function dailyZeroIfDue(root: string, sessionID: string): boolean {
  const state = readState(root)           // READ 1
  appendEpisodic(root, { ... })           // internal readState + writeState ← INTERMEDIATE WRITE
  const state2 = readState(root)          // READ 2 — state already diverged
  state2.session.last_zeroed = today
  writeState(root, state2)
}
// CORRECT — single operation per SPEC 1.2
export function dailyZeroIfDue(root: string, sessionID: string): boolean {
  const state = readState(root)           // SINGLE READ
  state.memory.episodic.push({ ... })    // inline modification
  state.memory.pending_mem0.push({ ... }) // inline modification
  state.session.last_zeroed = today
  state.memory.short_term = []
  writeState(root, state)                // SINGLE WRITE
  return true
}
4.2 Map all paths. For each function, mentally execute all branches. Mandatory paths to verify:
├── Happy path
├── State/file absent (first run)     ← defined in SPEC 1.4
├── Corrupted state or wrong type
├── I/O failure (disk, network, permission)
├── Concurrency (two simultaneous processes)
└── Out-of-limit data (empty array, very long string)
4.3 Errors must never be silenced. `.catch(() => {})` forbidden without logging. Every error path must: log with enough context for diagnosis. Not block the main flow (if background operation). Indicate risk level (Low, Medium, High).
// FORBIDDEN
flushMem0(root).catch(() => {})
// REQUIRED
flushMem0(root).catch((err: unknown) => {
  appendLedger(root, {
    action: "flush_mem0_failed",
    risk_tier: "Medium",
    rationale: `flushMem0 failed: ${err instanceof Error ? err.message : String(err)}`,
  })
})
4.4 Sensitive data in logs. Before serializing any object to log or audit file: can the object contain tokens, keys, passwords, credentials? If yes, apply redaction before serializing.
// FORBIDDEN
detail: JSON.stringify(event.properties).slice(0, 500)
// REQUIRED
const redacted = redactSensitive(event.properties)
detail: JSON.stringify(redacted).slice(0, 500)
4.5 Paths checklist before advancing:
- [ ] First-run path (per SPEC 1.4) implemented?
- [ ] All functions that read AND write state do so in single operation?
- [ ] No `.catch(() => {})` without logging?
- [ ] Sensitive data redacted before logs?
- [ ] Unknown resources have explicit commented default classification?
PHASE 5 — WRITE THE CODE.
5.1 Write order: 1. Types and interfaces (from SPEC 1.3). 2. Factories / `emptyState()` (from SPEC 1.3 + 1.4). 3. Pure utility functions (no I/O). 4. I/O functions (read/write). 5. Business functions (use I/O + logic). 6. Handlers/hooks (use business functions). Never write a handler before the functions it calls.
5.2 Writing rules: each function has single responsibility declared in JSDoc if not obvious. Known limitations documented with `// KNOWN LIMITATION:`. TODOs in format `// TODO: [what is missing] — [block or reason]`. Type cast has comment explaining why it is needed.
5.3 Forbidden placeholders without explicit TODO:
| Value | Problem |
`"pending"` in hash field | hash never computed — violates SPEC 1.3
`0` in real cost field | cost never measured — violates SPEC 1.3
`any` in public signature | type never defined — violates PHASE 3
`// TODO` without identified block | invisible technical debt
PHASE 6 — ADVERSARIAL SELF-REVIEW. After writing the code, run this review before delivering.
6.1 Check SPEC adherence. For each implemented function: does implemented behavior match SPEC 1.1 exactly? Do data fields match SPEC 1.3 definitions? Does first-run behavior match SPEC 1.4?
6.2 State contract verification. For each shared-state function: Q1 how many times is state read from disk? Should be 1. Q2 how many times is state written to disk? Should be 1. Q3 is there a read-write window where another process can write?
6.3 Type guard verification. For each `if (typeof x ...)` or `if (Array.isArray(x) ...)`: execute with 3 concrete values: expected happy-path value. corrupted value (wrong type). absent value (undefined/null). Verify guard produces correct behavior in all three.
6.4 Hook semantics verification. For each framework hook: who generated the data in `output`? assistant, user or system? Verify the `type` field in the record reflects the correct source.
6.5 Silenced error search. Search generated code for: `.catch(() => {})` → replace with contextual log. Empty `try { } catch { }` → add minimal log. `console.error(err)` without context → add function identification.
6.6 Final checklist:
- [ ] Each implemented function matches its SPEC?
- [ ] No `any` in public signature without `TODO:UNVERIFIED`?
- [ ] No state read more than once per logical operation?
- [ ] No silenced errors?
- [ ] All first-run paths implemented?
- [ ] All type guards verified with 3 concrete values?
- [ ] All hook semantics verified?
- [ ] Sensitive data redacted before logs?
- [ ] Known limitations documented in code?
PHASE 7 — DELIVERY.
7.1 Delivery format. When delivering corrected or new code: SPEC produced — summary of specifications defined in PHASE 1. Corrections list — table: original problem → correction → confidence. Remaining limitations — what could not be fixed and why. Pending TODOs — listed with identified block. Missing files — that would prevent complete verification, if any.
7.2 What not to deliver: code without prior documented SPEC. Code with unjustified `any`. Code with `.catch(() => {})` without logging. Code with state read multiple times per operation. Code assuming hook semantics without verifying signature. Code with data fields without source and initial-value definition.
QUICK REFERENCE — MOST COMMON ERRORS BY CATEGORY:
Fields without spec | SYMPTOM: field filled with `"pending"`, `0` or `""` in production | CAUSE: SPEC did not define field content nor who computes it | SOLUTION: mandatory PHASE 1 — define type, source, initial value for each field.
Shared state | SYMPTOM: function calls another function reading/writing the same file | CAUSE: state owner not declared in SPEC (1.2) | SOLUTION: declare owner → pass state as parameter → read once, write once.
Type guards | SYMPTOM: guard uses array check to protect an object (or vice versa) | CAUSE: condition not tested with concrete values | SOLUTION: execute with 3 values; use `typeof` + null check + `Array.isArray` together.
Framework hooks | SYMPTOM: assistant data classified as user data (or vice versa) | CAUSE: hook semantics not verified before implementing (PHASE 2) | SOLUTION: read hook definition → identify data origin → only then implement.
Silenced errors | SYMPTOM: `.catch(() => {})` or empty `catch {}` | CAUSE: failure path not modeled in SPEC (1.1) nor PHASE 4 | SOLUTION: log with minimal context (function, relevant parameters, error message).
Missing types | SYMPTOM: `Record<string, any>` in public signature | CAUSE: deferred typing — SPEC 1.3 not executed | SOLUTION: define interface before implementing; `any` only with explicit `TODO:UNVERIFIED`.
Absent state on first run | SYMPTOM: function throws when state file does not exist | CAUSE: SPEC 1.4 not executed (initialization responsibility not declared) | SOLUTION: every state-reading function must auto-initialize or have documented prerequisite.
