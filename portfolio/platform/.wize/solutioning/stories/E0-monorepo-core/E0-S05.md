# Story: LaudoEngine + PDF generator

## Context

Componente mais crítico da plataforma (PRD §3.3). Toda falha compromete a validade jurídica de todos os produtos. `engine.py` orquestra: PDF render → hash → chain → WORM → persist → LaudoResult. Tipos de laudo (10) e LaudoRequest/LaudoResult do PRD §3.3 são o contrato.

## Sources of truth

- `prd.md` (§3.3) · `architecture.md` (seq. 1) · ADR-004 · epic E0 · TEA contract
- Código `services/shared/laudo/engine.py` do PRD §3.3 (LaudoType, LaudoRequest, LaudoResult, LaudoEngine.emit) como base EXATA

## Acceptance criteria

- **F0-16:** Dado um LaudoRequest válido, Quando `engine.emit` é executado, Então retorna LaudoResult com laudo_id, laudo_number sequencial por tenant (ex: LAI-2026-0042), sha256_hash, chain_hash, worm_key, pdf_url assinada e emitted_at.
- **F0-17:** Quando o PDF é renderizado, Então contém o payload do laudo e referências normativas (normative_refs).
- **F0-18:** Quando o mesmo payload é emitido duas vezes, Então cada laudo tem id/número distintos e hashes de conteúdo idênticos (determinismo do PDF render).
- **F0-19:** Quando o engine falha antes de gravar no WORM, Então nenhum registro parcial persiste (transação atômica) e erro retorna como RFC 7807.
- **F0-20:** A latência de emissão (render+hash+chain+persist) é < 60s para laudo simples (NFR Perf-01).

## Restrictions

- **Out of scope:** integração real AWS S3 (S07 mock/interface); templates de laudo por produto (Fases 1+).
- **Protected behaviors:** numbering sequencial por tenant nunca reinicia; chain nunca é quebrada.
- **Compatibility:** ReportLab ou WeasyPrint (decisão do dev dentro da família do PRD); Pydantic schemas.

## Notes for Shuri (Dev)

- Touch points: `services/shared/laudo/engine.py`, `pdf_generator.py`, `schema pydantic` dos laudos, chamada a WORMVault/HashChain (interfaces — implementações em S06/S07).
- Reuse: LaudoType enum EXATO do PRD (LAI, LCA, LTM, LIR, LEO, LRF, LJP, LCO, LSD, LPC).
- Add: sequência por tenant garantida (lock/transaction na escrita do número).

## Validation contract

- **AC → test:** F0-16 → integration emit completo; F0-17 → unit pdf content; F0-18 → unit determinismo (hashes iguais, ids diferentes); F0-19 → integration rollback; F0-20 → perf test < 60s.
- **Required checks:** unit/integration/perf smoke, lint, build.
- **States:** request válido → laudo emitido; falha → erro 7807 sem estado parcial.

- Mocks: WORMVault e HashChain reais (são os próximos stories — implementar interfaces primeiro).
- NFR sample: emissão laudo simples < 60s (F0-20).
