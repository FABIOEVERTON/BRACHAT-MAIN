# Story: Modelo de tenant (schema-per-tenant)

## Context

Modelo de dados multi-tenant do PRD §3.2: tabela `public.tenants` + schema `tenant_{id}` por tenant, isolamento por construção (ADR-002), tenant context via ContextVar + search_path.

## Sources of truth

- `prd.md` (§3.2) · `architecture.md` (ADR-002, seq. 3) · epic E0 · TEA contract
- Código exemplo `services/shared/tenant/context.py` do PRD §3.2 como base

## Acceptance criteria

- **F0-12:** Dado um tenant criado, Quando o serviço recebe request com tenant id, Então `SET search_path TO tenant_{id}, public` é aplicado e o context var carrega o tenant.
- **F0-13:** Quando um segundo tenant é criado, Então seus dados ficam em schema distinto e uma query no schema A não retorna dados do schema B.
- **F0-14:** Quando uma migration de schema é aplicada, Então roda em todos os schemas de tenant existentes (migration per-schema).
- **F0-15:** Quando o tenant é suspenso, Então novas requisições para ele falham com 403 e status persistido.

## Restrictions

- **Out of scope:** RBAC por tenant (S03 já cobre roles); billing.
- **Protected behaviors:** nunca `SET search_path` global; sempre scoped à connection do request.
- **Compatibility:** SQLAlchemy async; PostgreSQL 16.

## Validation contract

- **AC → test:** F0-12 → unit context var + search_path; F0-13 → integration isolamento (dado A invisível em B); F0-14 → integration migration multi-schema; F0-15 → integration 403.
- **Required checks:** unit/integration, lint, build.
- **States:** tenant ativo → suspenso.
